## v0.2 相对 v0.1 的改动摘要

本版本基于 v0.1 做了一次进一步的范围收敛和落地颗粒度细化，关键改动：

1. **顶部新增「0. 本期范围声明」**：明确本期不接任何真实美团 / 大众点评 / 地图 API，专注打磨 Agent 推理链路。Mock 数据是主数据源，不是兜底。
2. **新增「约饭 MVP 如何承载全天候故事」**：把约饭场景到全天候管家的故事链路写清楚，避免答辩被问"你这不就是约饭工具吗"。
3. **页面从 5 个砍到 3 个**：创建页 + 填写页 + 看板/结果合并页。反馈页推到 v0.3。
4. **新增「积木拆解与接口契约」一节**：把整条流水线拆成 8 块可独立替换的积木，每块定义输入输出，**先做"假版本"再换"真版本"**，是 v0.2 的核心工程方法论。
5. **自检模块拆两层**：硬规则层（确定性代码 if/else）+ LLM 解释层。硬约束不交给 LLM 是答辩加分项。
6. **两周开发计划重排**：D0 先打通部署链路 + 10 天主线 + 4 天 buffer。每天产出"积木假版 → 真版"的明确升级。
7. **删除"接入真实本地生活数据"作为短期路线**：推到 v2+，本期完全不讨论。

## 0. 本期范围声明（必读）

本期 MVP 的目标是：

> **跑通"多人偏好 → AI Agent 推理 → 自检 → 可执行推荐"的完整闭环，证明这套架构可以承载"全天候本地生活管家"的设想。**

### 0.1 本期主动放弃的能力

为避免被外部依赖拖死，本期**主动放弃**以下能力：

- 不接美团 / 大众点评的任何 API；
- 不接地图 / 路线 / 营业时间 / 排队等真实数据；
- 不做真实下单 / 支付 / 预约；
- 不做小程序、不做微信群机器人；
- 不做用户登录、不做实时通信（WebSocket）。

所有"真实世界数据"在本期一律由 **Mock 餐厅数据集**承载。Mock 数据集是被精心设计过的——每条数据都对应一个演示意图（用于触发某种自检通过 / 失败），保证 Demo 可复现。

### 0.2 为什么这样收敛是合理的

- **评委关心的是"OpenClaw + Agent 怎么思考"，不是"接没接真实 API"**。比赛主题是"基于 OpenClaw 的本地生活管家"，OpenClaw 是 Agent 框架，不是数据源。我们的差异化是 Agent 推理链路 + 自检模块，不是数据集大小。
- **Mock 数据反而是优势**。我们可以精确设计冲突场景，确保每次 Demo 都能稳定演示"Agent 发现冲突 → 自检拒掉错误候选 → 重排"——真实 API 做不到这种确定性。
- **学术界做评测就是这么做的**。"在受控数据集上证明推理链路有效"是个被认可的科学方法。我们可以主动这么讲：本期专注算法与流程，数据接入留待工程化阶段。
- **降低不可控风险**。真实 API 的资质、配额、稳定性都不是学生队能控制的，放进 MVP 只会引入失败概率。

### 0.3 与全天候管家的关系

约饭只是第一锤。同一套 Agent 架构在 v2+ 可以无缝迁移到其他场景：

```text
本期能力（约饭）              未来场景如何复用
────────────────────────     ──────────────────────────
意图理解（自然语言→任务）    → 午饭/周末/夜间各场景的需求识别
多人偏好收集 + 约束建模      → 团建、家庭出游、情侣约会
冲突识别 + 公平性评分        → 任何多人协同决策场景
自检模块（硬规则+LLM）       → 任何"AI 给建议"的场景都需要
OpenClaw 工具链调度          → 接入更多本地生活工具
个人 / 小团体记忆            → 长期个性化服务的基础
```

本期完成的工程不是"约饭工具"，而是**这套 Agent 架构的最小可行版本**。这个故事必须在答辩时讲清楚。

## 1. 一句话需求

做一个可以在微信里分享的 H5 多人约饭协同页：

> 发起人通过微信私聊 / 模拟入口创建约饭任务，系统生成一个 H5 链接；朋友们打开链接填写各自偏好；Agent 自动抽取多人约束、识别冲突、查询 mock 餐厅数据、生成候选方案，并经过自检模块检查后输出最终推荐、风险说明和群聊邀约文案。

这不是普通"AI 推荐餐厅"，核心是：

1. 多人偏好收集；
2. 冲突识别；
3. 约束建模；
4. 自检评测；
5. 可执行推荐；
6. OpenClaw 作为 Agent 调度中枢。

## 2. 背景与产品定位

### 2.1 背景

比赛方向为"基于 OpenClaw 的本地生活全天候私人管家"。团队不希望做泛泛的聊天机器人，而是希望做一个能主动出现、理解日常本地生活需求、跨工具执行、持续记忆、多人协同、自检方案可靠性的 AI Agent。

### 2.2 MVP 收敛逻辑

完整"全天候管家"包含早晨提醒、午饭推荐、晚间约饭、周末规划、夜间突发等多个场景。但 MVP 不应贪多，第一版只打穿一个场景：

> 多人约饭 / 本地生活协同管家。

该场景的选择理由：

- **足够高频**：大学生 / 年轻白领每周都要解决；
- **足够具象**：评委秒懂场景，不需要解释；
- **天然多人**：能体现"多人协同"这个 Agent 区别于普通推荐助手的关键能力；
- **天然有冲突**：口味、预算、时间、距离五个维度天然产生约束冲突，是展示 Agent 推理深度的绝佳载体。

### 2.3 目标用户

第一版以大学生 / 研究生 / 年轻白领为主：

- 经常在学校、公司、宿舍、合租圈附近约饭；
- 群里讨论很久也定不下来；
- 每个人都有口味、预算、时间、距离限制；
- 希望有人帮忙协调，并给出可靠方案。

### 2.4 答辩故事主轴（必背）

队伍所有成员需要能用一句话回答以下 5 个问题：

1. **为什么不是普通聊天机器人？**——因为普通聊天机器人没有"多人协同 + 约束建模 + 自检"这三层，它只能回答"附近有什么餐厅"，回答不了"我们三个有冲突偏好时该选哪家"。
2. **OpenClaw 在哪里发挥作用？**——OpenClaw 是 Agent 调度中枢，注册了 8 个工具（见第 11 章），负责把"用户需求"路由到正确的工具链上。
3. **多人协同如何实现？**——通过 H5 协同页 + 任务 / 偏好的结构化 API，每个成员独立填写偏好，Agent 汇总后做约束建模。
4. **自检评测如何避免 AI 瞎推荐？**——硬规则层 + LLM 解释层（见第 12 章），硬约束不交给 LLM。
5. **未来如何扩展到全天候管家？**——见 0.3 节，同一套架构换数据源即可。

## 3. MVP 范围

### 3.1 本期必须做

| 模块 | 必须能力 |
|---|---|
| 任务创建 | 发起人输入一句自然语言需求，创建约饭任务 |
| 分享链接 | 系统生成 H5 任务链接，可复制到微信群 |
| 多人填写 | 多个成员打开链接填写昵称和自然语言偏好 |
| 约束抽取 | Agent 把自然语言转成结构化约束 |
| 冲突识别 | 明确指出口味、预算、时间、距离、氛围冲突 |
| 餐厅检索 | 从 mock 餐厅数据中筛选候选 |
| 方案生成 | 输出 2-3 个候选方案 |
| 自检评测 | 检查预算、时间、距离、忌口、安静度、排队风险、公平性 |
| 最终推荐 | 输出首推方案、备选方案、满足/牺牲点、风险说明 |
| 群聊文案 | 生成可复制到微信群的邀约文案 |

### 3.2 本期不做（参见 0.1）

明确不做：真实美团下单、真实支付、真实排队、真实大众点评 / 美团交易接口、完整微信小程序、微信群机器人、复杂登录、WebSocket 实时通信、完整全天候 5 场景、饭后反馈页（推到 v0.3）。

### 3.3 Demo 可模拟但要说清楚

- 餐厅数据使用 mock 数据（已在 0.1 节明确）；
- 主动提醒可以用定时按钮或时间线模拟；
- 微信私聊如果接入不稳，可以用"模拟微信聊天入口"兜底。

## 4. 用户入口与多人协同方式

### 4.1 推荐入口组合

```text
微信私聊 / 模拟微信入口
        +
H5 多人协同任务页
        +
OpenClaw Agent 中枢
```

### 4.2 H5 协同页是什么

H5 协同页是一个公网可访问的网页地址，例如：

```text
https://demo-domain.com/dinner/abc123
```

它不是 GitHub 仓库。GitHub 仓库存代码，H5 协同页是代码部署后真正给用户打开的网页。

### 4.3 多人协同三层降级

#### Level 1：微信群分享 H5 链接（主方案）

```text
发起人微信私聊管家
→ 管家生成任务链接
→ 发起人把链接丢到微信群
→ 成员打开链接填写偏好
→ Agent 汇总分析
```

#### Level 2：复制群聊文本给管家（备选）

用户把微信群讨论复制给管家：

```text
A：我想吃辣，但不想吃火锅
B：我完全不吃辣，预算 80 内
C：我 8 点半前要回宿舍
```

Agent 直接解析这段文本。

#### Level 3：发起人代填多人偏好（现场兜底）

一个页面提供三个输入框，发起人一次性填完，用于答辩现场环境不稳定时兜底。

## 5. 核心用户路径

### 5.1 标准路径

#### Step 1：发起任务

用户输入：

```text
明晚三个人想在学校附近吃饭，人均 100 以内，适合聊天，别太吵。
```

#### Step 2：生成分享链接

```text
我已经建好了约饭任务。
把这个链接发到群里，让大家填一下偏好：
https://demo-domain.com/dinner/abc123
```

#### Step 3：成员填写偏好

成员 A：我想吃辣，但不想吃火锅。
成员 B：我完全不吃辣，预算最好别超过 80。
成员 C：我 8 点半前要回宿舍，最好别排队，离学校近一点。

#### Step 4：Agent 抽取约束

```text
硬约束：
- B 完全不吃辣
- B 预算最好 ≤80
- C 20:30 前要回宿舍
- C 不希望排队
- 地点要离学校近

软偏好：
- A 想吃辣
- A 不想吃火锅
- 大家想要适合聊天
- 环境不要太吵
```

#### Step 5：Agent 识别冲突

```text
我发现你们有 3 个主要冲突：
1. A 想吃辣，但 B 完全不吃辣；
2. 总预算是人均 100，但 B 更希望不超过 80；
3. 想吃得舒服，但 C 8:30 前要回宿舍，不能太远或排队太久。
```

#### Step 6：候选方案 + 自检

系统输出 2-3 个候选方案，每个方案展示自检结果（哪些项通过、哪些失败）。

#### Step 7：最终推荐 + 群聊文案

```text
综合来看，我推荐「东门小院融合菜」。
原因：人均 82，步行 12 分钟，可选辣度，有不辣菜，环境安静，
排队风险低，能保证 C 8:30 前回宿舍。
```

```text
群聊文案：
我帮大家看了一下，推荐明晚去「东门小院融合菜」。
人均 82 左右，离学校步行 12 分钟，环境比较安静，
有不辣菜也能选辣味，不用排太久，小周 8:30 前回宿舍也来得及。
备选是「轻食西餐」，更稳但小林想吃辣会满足弱一点。
大家 OK 的话我来约 18:30？
```

## 6. 页面需求（v0.2：从 5 页砍到 3 页）

### 6.1 页面 1：创建任务页 `/create`

#### 目标

让发起人创建约饭任务。

#### 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 发起人昵称 | input | 否 | 默认为"我" |
| 原始需求 | textarea | 是 | 自然语言，例如"明晚三个人学校附近吃饭..." |
| 地点 | input | 否 | 可从自然语言抽取，第一版可手动填"学校附近" |
| 预计人数 | number | 否 | 默认 3 |
| 约饭时间 | datetime/string | 否 | 默认从自然语言抽取 |
| 创建任务按钮 | button | 是 | 调用 create task API |

#### 输出

创建成功后展示：任务标题、分享链接、复制按钮、"进入任务看板"按钮。

---

### 6.2 页面 2：成员偏好填写页 `/dinner/:taskId/fill`

#### 目标

让成员填写自己的约束和偏好。

#### 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 昵称 | input | 是 | 例如"小林" |
| 自然语言偏好 | textarea | 是 | 例如"我完全不吃辣，预算 80 内" |
| 预算上限 | number | 否 | 可选快捷字段 |
| 是否吃辣 | select | 否 | 能吃辣 / 不吃辣 / 无所谓 |
| 最晚离开时间 | time | 否 | 例如 20:30 |
| 提交按钮 | button | 是 | 保存 participant |

#### 提交后展示

"已提交"、当前已收集人数、其他人昵称列表、"查看任务看板"按钮。

> **设计说明**：本页同时保留自然语言 textarea 和 4 个快捷字段。这是一个**主动的降级设计**：万一 LLM 抽取不稳定，规则可以直接用快捷字段兜底。这正好对应"积木式"思想——抽取积木假/真版都能让流水线跑通。

---

### 6.3 页面 3：任务看板 + 结果合并页 `/dinner/:taskId`

> **v0.2 关键变化**：把 v0.1 的"任务看板页"和"推荐结果页"合并成一个**滚动长页面**。这样前端实际只有 3 个 URL，零基础队友更好上手。同时也符合移动端用户习惯——一个长页里所有信息都能看到，不用来回点。

#### 模块（按从上到下顺序）

1. **任务信息卡**（标题、原始需求、地点、人数、状态）；
2. **已提交成员卡**（每人一个卡片：昵称 + 原始偏好 + Agent 抽取出的硬/软约束）；
3. **冲突识别卡**（高/中/低优先级冲突列表 + 解决策略）；
4. **"生成推荐方案"按钮**（任务状态 < ready_to_recommend 时禁用）；
5. **候选方案卡片组**（生成后出现，2-3 张卡片）；
6. **自检结果面板**（每个候选方案的硬规则检查 + LLM 解释）；
7. **最终推荐卡**（首推 + 推荐理由 + 风险说明）；
8. **群聊邀约文案卡**（带"一键复制"按钮）。

#### 状态机

```text
waiting_preferences  等待成员填写
ready_to_recommend   可以生成推荐
recommending         生成中
done                 已生成结果
failed               生成失败
```

#### 候选方案卡片字段

| 字段 | 说明 |
|---|---|
| 餐厅名称 | 例如"东门小院融合菜" |
| 类型 | 融合菜 / 西餐 / 烤肉等 |
| 人均 | 例如 82 元 |
| 距离 | 例如 950m / 步行 12 分钟 |
| 营业时间 | 例如 11:00-22:00 |
| 是否可选辣度 | 是 / 否 |
| 是否有不辣选项 | 是 / 否 |
| 安静度 | 1-5 分 |
| 排队风险 | low / medium / high |
| 成员满意度 | A/B/C 分别多少分 |
| 自检状态 | 通过 / 不通过 / 有风险（每项独立标注） |
| 推荐理由 | LLM 生成解释 |

## 7. 积木拆解与接口契约（v0.2 新增，核心方法论）

### 7.1 为什么要"积木式"

零基础队友最大的风险是**互相阻塞**。如果前端必须等后端写完才能动、后端必须等 Agent 写完才能动，整个项目会反复卡住。

解决方案是把流水线拆成 **8 块独立可替换的积木**，每块定义清楚输入输出 JSON schema：

- **每块积木先做"假版本"**（hardcode 一段返回值），保证整条流水线 D3 之前就能跑通；
- **后面 9 天的工作就是"把假积木换成真积木"**，每次替换不影响其他模块；
- 队友可以并行开发、各自 mock 上下游，永远不会被别人阻塞。

这个做法的杀手锏是：**任何一块出问题都不会卡死整条流水线**。OpenClaw 接入不顺？没事，前端先用普通按钮触发流水线。LLM 抽取不稳？没事，先用规则 + 关键词匹配兜底。

### 7.2 8 块积木概览

```text
积木1 任务创建        in: 自然语言 raw_request → out: task_id + share_url
积木2 偏好收集        in: nickname + 自然语言 → out: participant 记录
积木3 约束抽取        in: 原始文本（任务+所有成员）→ out: hard/soft constraints[]
积木4 冲突识别        in: constraints[] → out: conflicts[]
积木5 餐厅检索        in: constraints → out: candidates[]（查 mock 库）
积木6 满意度打分      in: candidates + per-member constraints → out: scored candidates
积木7 自检模块        in: scored candidates + constraints → out: passed/failed + reasons
积木8 群聊文案生成    in: final choice + context → out: 文案 string
```

### 7.3 每块积木的"假版本→真版本"路线

| 积木 | 假版本（D1-D3 完成） | 真版本（D4-D11 替换） |
|---|---|---|
| 1 任务创建 | 写入数据库即可，不抽取任何信息 | 顺便用 LLM 提取标题/时间/地点 |
| 2 偏好收集 | 写入数据库即可 | 同上 |
| 3 约束抽取 | 用关键词匹配（"不吃辣"、"预算 80"等正则） | 用 LLM + JSON Schema |
| 4 冲突识别 | 硬编码几条 if-else 规则 | LLM + 规则混合 |
| 5 餐厅检索 | 全表返回 + 简单 filter | 加距离 / 时间 / 价格的多维筛选 |
| 6 满意度打分 | 给每个候选打 50-90 的随机分 | 按 12.3 节公式计算 |
| 7 自检模块 | 全部返回 pass | 硬规则层（确定性）+ LLM 解释层 |
| 8 文案生成 | 模板字符串 + 字段拼接 | LLM 生成 |

> **关键纪律**：D3 末尾要有一次集成测试——所有 8 块假积木串起来，能完成一次完整的"创建任务 → 三人填写 → 看到推荐"流程。如果 D3 跑不通，后续 9 天都不要写真版本，先把假版本流水线打通。

### 7.4 接口契约示例

## 12. 推荐与自检逻辑（v0.2 关键改动：拆两层）

### 12.1 核心设计：硬规则层 + LLM 解释层

> **v0.2 与 v0.1 的本质区别**：v0.1 把所有自检都丢给 LLM 做，本质上是"LLM 给推荐 + LLM 评推荐"，逻辑上不闭环（LLM 自己评自己）。v0.2 把自检拆成两层，**硬约束完全不交给 LLM**，确保确定性。

#### 第一层：硬规则层（确定性，纯代码 if/else）

硬规则层不调用任何 LLM，全部用代码实现，对每个候选方案逐项检查：

```python
def hard_rules_check(restaurant, constraints):
    result = {}
    # 预算硬约束
    result['budget_check'] = (
        'pass' if restaurant.avg_price <= constraints.budget_max else 'fail'
    )
    # 忌口硬约束
    if 'no_spicy' in constraints.diet_hard:
        result['diet_check'] = (
            'pass' if restaurant.supports_non_spicy else 'fail'
        )
    # 时间硬约束（必须在 deadline 前能吃完回去）
    eat_time = 60  # 假设吃饭 60 分钟
    buffer = 10
    end_time = arrive_time + restaurant.walk_minutes + eat_time + buffer
    result['time_check'] = (
        'pass' if end_time <= constraints.back_before else 'fail'
    )
    # 营业时间
    result['open_hours_check'] = (
        'pass' if covers_dinner_time(restaurant, constraints.scene_time) else 'fail'
    )
    return result
```

**硬规则层任何一项 fail，该餐厅直接淘汰**，不进入候选。

#### 第二层：LLM 解释层（用于讲故事）

LLM 解释层基于硬规则的输出，生成自然语言解释：

- 为什么这个方案通过 / 失败；
- 满足了谁的什么需求；
- 牺牲了谁的什么需求；
- 风险是什么。

LLM 不能改变硬规则的判断结果，只能解释。

#### 第三层：软检查（混合）

部分检查介于硬软之间，用规则给基线 + LLM 微调：

- 氛围匹配（quiet_score / chat_friendly）；
- 排队风险（queue_risk）；
- 公平性（最低个人满意度阈值）。

### 12.2 推荐流程

```text
1. 读取任务和成员偏好
2. 抽取约束（积木 3）
3. 识别冲突（积木 4）
4. 从餐厅库中过滤明显违规项（积木 5）
5. 给每个成员计算满意度（积木 6）
6. 给每个方案计算总分（积木 6）
7. 自检：硬规则层 → 软检查 → LLM 解释（积木 7）
8. 选择最终推荐和备选方案
9. 生成解释与群聊文案（积木 8）
```

### 12.3 满意度评分公式

```text
单人成员满意度 = 50 基础分
+ 满足软偏好加分
- 轻微违背软偏好扣分
- 风险因素扣分
```

示例：

```text
满足想吃辣：+15
支持不辣：+20
人均低于预算：+15
步行 15 分钟内：+10
安静适合聊天：+10
排队风险 medium：-8
排队风险 high：-20
人均超过个人预算：-20
```

### 12.4 群体公平性评分

不要只看平均满意度，还要看最低满意度。

```text
方案总分 = 平均满意度 * 0.6 + 最低个人满意度 * 0.3 + 可执行性分 * 0.1
```

这样可以避免"两个人很满意，一个人完全不能接受"。**这是答辩时要重点讲的算法亮点。**

### 12.5 自检项汇总

| 自检项 | 层级 | 通过标准 |
|---|---|---|
| 预算检查 | 硬规则 | 不超过总体预算；首推尽量接近个人预算 |
| 忌口检查 | 硬规则 | 不违反不吃辣、过敏等硬约束 |
| 时间检查 | 硬规则 | 能按时结束并返回 |
| 营业时间检查 | 硬规则 | 到店时间在营业时间内 |
| 距离检查 | 软检查 | 步行 / 通勤时间合理 |
| 排队检查 | 软检查 | 不选择高排队风险作为首推 |
| 氛围检查 | 软检查 | 安静度和聊天友好度满足 |
| 公平性检查 | 软检查 | 最低个人满意度不能过低 |
| LLM 解释 | LLM 层 | 给所有上述检查生成自然语言解释 |

### 12.6 自检失败后的动作

| 失败类型 | 动作 |
|---|---|
| 预算超限（硬） | 直接淘汰 |
| 忌口冲突（硬） | 直接淘汰 |
| 时间不可行（硬） | 直接淘汰 |
| 氛围不合适（软） | 降级为备选 |
| 排队风险高（软） | 降级为备选 |
| 某人满意度过低（软） | 重新找更公平方案 |
| 信息不足 | 追问，例如"你们大概几点出发？" |

## 14. 技术架构建议

### 14.1 最小架构

```text
微信私聊 / 模拟微信入口
        ↓
OpenClaw Agent
        ↓
后端 API（8 个 endpoint，对应 8 块积木）
        ↓
SQLite + mock 餐厅数据
        ↑
H5 协同页（3 个页面）
        ↑
微信群分享链接
```

### 14.2 技术栈建议（针对零基础队友友好优先）

前端：

```text
推荐 Next.js（一个工程同时管前端页面和后端 API，部署简单）
或 Vite + React（前后端分离）
```

后端：

```text
推荐 Next.js API Routes（与前端同工程，零基础同学最友好）
或 FastAPI（Python，Agent 同学如果熟 Python 可选）
```

数据库：

```text
本期用 SQLite 即可，文件型数据库，零部署成本。
v0.3 可换 Supabase / PostgreSQL。
```

部署：

```text
前端 + 后端：Vercel（一键部署，免费额度足够 Demo 用）
备选：Cloudflare Pages / Netlify
```

### 14.3 是否需要实时通信

不需要。第一版使用：用户提交后刷新、或 3 秒轮询、或发起人手动点击"刷新 / 生成方案"。

### 14.4 是否需要登录

不需要。第一版使用：

```text
task_id + invite_token + 昵称
```

正式版再考虑微信登录。

## 16. 验收标准

### 16.1 产品验收（最小闭环）

必须能完成以下闭环：

```text
创建任务
→ 分享链接
→ 3 人在不同设备打开链接提交偏好
→ 抽取约束（结构化展示）
→ 识别冲突（结构化展示）
→ 推荐候选餐厅（2-3 个）
→ 自检（硬规则 + 软检查 + LLM 解释）
→ 输出最终推荐
→ 生成群聊文案
```

### 16.2 技术验收

| 验收项 | 标准 |
|---|---|
| H5 链接可访问 | 手机微信 / 浏览器可打开（需测试微信内置浏览器兼容） |
| 多人提交可保存 | 至少 3 人偏好可以保存并展示 |
| API 可调用 | 8 个 endpoint 全部正常响应 |
| 8 块积木独立可测 | 每块积木可单独单元测试 |
| Agent 可运行 | 至少能完成约束抽取、冲突识别、推荐解释 |
| 自检可解释 | 每个候选方案有明确的硬规则 + 软检查通过 / 失败原因 |
| Demo 稳定 | 现场不依赖网络波动过大的外部服务，至少有兜底数据和录屏 |

### 16.3 答辩验收

答辩时必须能讲清楚 2.4 节的 5 个问题。

## 19. 风险与降级方案

### 风险 1：OpenClaw 微信入口不稳定

**降级**：做模拟微信聊天页，前端直接调后端 API，OpenClaw 退化为"幕后调度"。Demo 时仍可演示完整流程。

### 风险 2：真实多人协同调试麻烦

**降级**：同一个页面提供 3 个角色输入框（v0.1 第 4.4 Level 3），发起人现场代填三个人的偏好。

### 风险 3：LLM 抽取不稳定

**降级**：积木 3 永远保留"关键词匹配 + 快捷字段"的假版本作为兜底。在前端填写页同时收集 textarea 和快捷字段，规则优先于 LLM。

### 风险 4：推荐结果不稳定

**降级**：固定 demo task_id + 固定 mock 数据 + 固定候选结果。现场展示时仍调用部分逻辑（积木 5/6/7 真实跑），只在异常时回退到固定结果。

### 风险 5：H5 部署不稳定

**降级**：本地启动 + ngrok / Cloudflare Tunnel；答辩现场准备录屏作为最终兜底。

### 风险 6：D3 集成测试跑不通

**降级**：暂停所有真版本开发，全员先把假版本流水线打通。这是 v0.2 加的硬纪律。

## 22. 一句话总结

这个 MVP 的本质不是"做一个网页推荐餐厅"，而是：

> 用 H5 解决微信群多人偏好收集，用后端保存任务状态，用 OpenClaw 调度 Agent 工具链，用硬规则 + LLM 两层自检保证推荐可靠，**在受控的 mock 数据集上跑通"+ AI Agent"完整闭环**，证明这套架构可以承载未来的全天候本地生活管家。

> 真实 API、真实下单、真实记忆——都是 v0.3+ 的事。本期专注：**积木式拼出最小可行闭环。**
