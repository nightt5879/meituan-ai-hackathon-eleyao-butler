# H5 协同页：多人约饭 MVP 需求文档 v0.1

> 项目：基于 OpenClaw 的本地生活“全天候私人管家”  
> 当前 MVP 聚焦：多人约饭 / 本地生活协同管家  
> 交付对象：前端、后端、Agent / OpenClaw 接入同学  
> 文档目标：让接手同学不用再重新理解产品背景，可以直接拆任务、写代码、做 Demo。

---

## 1. 一句话需求

做一个可以在微信里分享的 H5 多人约饭协同页：

> 发起人通过微信私聊 / 模拟入口创建约饭任务，系统生成一个 H5 链接；朋友们打开链接填写各自偏好；Agent 自动抽取多人约束、识别冲突、查询 mock 餐厅数据、生成候选方案，并经过自检模块检查后输出最终推荐、风险说明和群聊邀约文案。

这不是普通“AI 推荐餐厅”，核心是：

1. 多人偏好收集；
2. 冲突识别；
3. 约束建模；
4. 自检评测；
5. 可执行推荐；
6. OpenClaw 作为 Agent 调度中枢。

---

## 2. 背景与产品定位

### 2.1 背景

比赛方向为“基于 OpenClaw 的本地生活全天候私人管家”。团队不希望做泛泛的聊天机器人，而是希望做一个能主动出现、理解日常本地生活需求、跨工具执行、持续记忆、多人协同、自检方案可靠性的 AI Agent。

### 2.2 MVP 收敛

完整“全天候管家”包含早晨提醒、午饭推荐、晚间约饭、周末规划、夜间突发等多个场景。但 MVP 不应贪多，第一版只打穿一个场景：

> 多人约饭 / 本地生活协同管家。

该场景足够高频、贴近日常，也能体现 Agent 区别于普通推荐助手的能力。

### 2.3 目标用户

第一版以大学生 / 研究生 / 年轻白领为主：

- 经常在学校、公司、宿舍、合租圈附近约饭；
- 群里讨论很久也定不下来；
- 每个人都有口味、预算、时间、距离限制；
- 希望有人帮忙协调，并给出可靠方案。

## 3. MVP 范围

### 3.1 本期必须做

| 模块 | 必须能力 |
|---|---|
| 任务创建 | 发起人输入一句自然语言需求，创建约饭任务 |
| 分享链接 | 系统生成 H5 任务链接，可复制到微信群 |
| 多人填写 | 多个成员打开链接填写昵称和自然语言偏好 |
| 约束抽取 | Agent 把自然语言转成结构化约束 |
| 冲突识别 | 明确指出口味、预算、时间、距离、氛围冲突 |
| 餐厅检索 | 从 mock 餐厅数据中筛选候选 |
| 方案生成 | 输出 2-3 个候选方案 |
| 自检评测 | 检查预算、时间、距离、忌口、安静度、排队风险、公平性 |
| 最终推荐 | 输出首推方案、备选方案、满足/牺牲点、风险说明 |
| 群聊文案 | 生成可复制到微信群的邀约文案 |

### 3.2 本期不做

本期明确不做以下内容，避免被平台限制拖死：

- 不做真实美团下单；
- 不做真实支付；
- 不做真实排队 / 预约；
- 不接真实大众点评 / 美团交易接口；
- 不做完整微信小程序；
- 不依赖微信群机器人读取群聊；
- 不做复杂登录；
- 不做 WebSocket 实时通信；
- 不做完整全天候 5 场景。

### 3.3 Demo 可模拟但要说清楚

以下能力可以在 Demo 中模拟：

- 餐厅数据使用 mock 数据；
- 预约 / 排队提醒为模拟执行；
- 主动提醒可以用定时按钮或时间线模拟；
- 微信私聊如果接入不稳，可以用“模拟微信聊天入口”兜底。

## 4. 用户入口与多人协同方式

### 4.1 推荐入口组合

MVP 推荐采用：

```text
微信私聊 / 模拟微信入口
        +
H5 多人协同任务页
        +
OpenClaw Agent 中枢
```

### 4.2 H5 协同页是什么

H5 协同页是一个公网可访问的网页地址，例如：

```text
https://demo-domain.com/dinner/abc123
```

它不是 GitHub 仓库。GitHub 仓库存代码，H5 协同页是代码部署后真正给用户打开的网页。

### 4.3 人和 AI 如何访问

人访问 H5 页面：

```text
用户在微信群里点击链接
→ 打开任务页
→ 填写偏好
→ 查看推荐结果
```

AI / OpenClaw 通常不直接“看页面”，而是调用后端 API：

```text
OpenClaw
→ 调用后端 API 创建任务、读取偏好、生成推荐、保存记忆
```

### 4.4 多人协同方式

第一版推荐采用三层降级：

#### Level 1：微信群分享 H5 链接，成员各自填写

这是主方案。

```text
发起人微信私聊管家
→ 管家生成任务链接
→ 发起人把链接丢到微信群
→ 成员打开链接填写偏好
→ Agent 汇总分析
```

#### Level 2：复制群聊文本给管家

作为备选能力。

用户把微信群讨论复制给管家：

```text
A：我想吃辣，但不想吃火锅
B：我完全不吃辣，预算 80 内
C：我 8 点半前要回宿舍
```

Agent 直接解析这段文本。

#### Level 3：发起人代填多人偏好

作为现场兜底。

一个页面提供三个输入框：

```text
我：...
朋友 A：...
朋友 B：...
```

发起人一次性填完。

## 5. 核心用户路径

### 5.1 标准路径

#### Step 1：发起任务

用户输入：

```text
明晚三个人想在学校附近吃饭，人均 100 以内，适合聊天，别太吵。
```

系统创建任务：

```text
任务：明晚三人约饭
地点：学校附近
预算：≤100 元/人
氛围：适合聊天、不要太吵
状态：等待成员补充偏好
```

#### Step 2：生成分享链接

系统返回：

```text
我已经建好了约饭任务。
把这个链接发到群里，让大家填一下偏好：
https://demo-domain.com/dinner/abc123
```

#### Step 3：成员填写偏好

成员 A：

```text
我想吃辣，但不想吃火锅。
```

成员 B：

```text
我完全不吃辣，预算最好别超过 80。
```

成员 C：

```text
我 8 点半前要回宿舍，最好别排队，离学校近一点。
```

#### Step 4：Agent 抽取约束

系统展示结构化理解：

```text
硬约束：
- B 完全不吃辣
- B 预算最好 ≤80
- C 20:30 前要回宿舍
- C 不希望排队
- 地点要离学校近

软偏好：
- A 想吃辣
- A 不想吃火锅
- 大家想要适合聊天
- 环境不要太吵
```

#### Step 5：Agent 识别冲突

系统展示：

```text
我发现你们有 3 个主要冲突：
1. A 想吃辣，但 B 完全不吃辣；
2. 总预算是人均 100，但 B 更希望不超过 80；
3. 想吃得舒服，但 C 8:30 前要回宿舍，不能太远或排队太久。
```

#### Step 6：生成候选方案并自检

系统输出 2-3 个候选方案，每个方案都展示自检结果。

#### Step 7：输出最终推荐

系统输出：

```text
综合来看，我推荐「东门小院融合菜」。
原因：人均 82，步行 12 分钟，可选辣度，有不辣菜，环境安静，排队风险低，能保证 C 8:30 前回宿舍。
```

#### Step 8：生成群聊邀约文案

系统输出可复制文案：

```text
我帮大家看了一下，推荐明晚去「东门小院融合菜」。
人均 82 左右，离学校步行 12 分钟，环境比较安静，有不辣菜也能选辣味，不用排太久，小周 8:30 前回宿舍也来得及。
备选是「轻食西餐」，更稳但小林想吃辣会满足弱一点。
大家 OK 的话我来约 18:30？
```

## 6. 页面需求

### 6.1 页面 1：创建任务页 / 模拟微信入口

#### 目标

让发起人创建约饭任务。

#### 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 发起人昵称 | input | 否 | 默认为“我” |
| 原始需求 | textarea | 是 | 自然语言，例如“明晚三个人学校附近吃饭...” |
| 地点 | input | 否 | 可从自然语言抽取，第一版可手动填“学校附近” |
| 预计人数 | number | 否 | 默认 3 |
| 约饭时间 | datetime/string | 否 | 默认从自然语言抽取 |
| 创建任务按钮 | button | 是 | 调用 create task API |

#### 输出

创建成功后展示：

- 任务标题；
- 分享链接；
- 复制按钮；
- “进入任务看板”按钮。

---

### 6.2 页面 2：成员偏好填写页

#### URL

```text
/dinner/:taskId
```

#### 目标

让成员填写自己的约束和偏好。

#### 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 昵称 | input | 是 | 例如“小林” |
| 自然语言偏好 | textarea | 是 | 例如“我完全不吃辣，预算 80 内” |
| 预算上限 | number | 否 | 可选快捷字段 |
| 是否吃辣 | select | 否 | 能吃辣 / 不吃辣 / 无所谓 |
| 最晚离开时间 | time | 否 | 例如 20:30 |
| 提交按钮 | button | 是 | 保存 participant |

#### 提交后展示

- “已提交”；
- 当前已收集人数；
- 其他人昵称列表；
- “查看任务看板”按钮。

---

### 6.3 页面 3：任务看板页

#### 目标

展示任务状态和成员偏好。

#### 模块

1. 任务信息卡；
2. 已提交成员列表；
3. 每个人的原始偏好；
4. Agent 抽取后的硬约束 / 软偏好；
5. 冲突识别卡；
6. “生成推荐方案”按钮。

#### 状态

```text
waiting_preferences  等待成员填写
ready_to_recommend   可以生成推荐
recommending         生成中
done                 已生成结果
failed               生成失败
```

---

### 6.4 页面 4：推荐结果页

#### 目标

展示候选方案、自检结果和最终推荐。

#### 模块

1. 冲突总结；
2. 候选方案卡片；
3. 自检结果面板；
4. 最终推荐卡；
5. 风险与备选方案；
6. 群聊邀约文案；
7. 饭后反馈按钮。

#### 候选方案卡片字段

| 字段 | 说明 |
|---|---|
| 餐厅名称 | 例如“东门小院融合菜” |
| 类型 | 融合菜 / 西餐 / 烤肉等 |
| 人均 | 例如 82 元 |
| 距离 | 例如 950m / 步行 12 分钟 |
| 营业时间 | 例如 11:00-22:00 |
| 是否可选辣度 | 是 / 否 |
| 是否有不辣选项 | 是 / 否 |
| 安静度 | 1-5 分 |
| 排队风险 | low / medium / high |
| 成员满意度 | A/B/C 分别多少分 |
| 自检状态 | 通过 / 不通过 / 有风险 |
| 推荐理由 | LLM 生成解释 |

---

### 6.5 页面 5：饭后反馈页，可选

MVP 可选做。

#### 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| 是否去了推荐店 | select | 去了 / 没去 |
| 整体满意度 | rating | 1-5 |
| 口味满意度 | rating | 1-5 |
| 环境满意度 | rating | 1-5 |
| 下次是否还推荐类似 | select | 是 / 否 |
| 补充反馈 | textarea | 自然语言 |

#### 作用

用于展示“记忆更新”概念：

```text
小团体偏好更新：
- 更喜欢安静、步行 15 分钟内的餐厅
- B 不吃辣作为强记忆保存
- A 喜欢可选辣度的融合菜
```

## 7. 后端 API 需求

### 7.1 创建任务

```http
POST /api/tasks
```

#### Request

```json
{
  "creator_name": "小林",
  "raw_request": "明晚三个人想在学校附近吃饭，人均 100 以内，适合聊天，别太吵。",
  "location_text": "学校附近",
  "expected_people_count": 3
}
```

#### Response

```json
{
  "task_id": "abc123",
  "share_url": "https://demo-domain.com/dinner/abc123",
  "status": "waiting_preferences"
}
```

---

### 7.2 获取任务详情

```http
GET /api/tasks/:taskId
```

#### Response

```json
{
  "task_id": "abc123",
  "title": "明晚三人约饭",
  "raw_request": "明晚三个人想在学校附近吃饭，人均 100 以内，适合聊天，别太吵。",

  "expected_people_count": 3,
  "status": "waiting_preferences",
  "participants": []
}
```

| preference_json | json | 偏好记忆 |
| updated_at | datetime | 更新时间 |

## 10. Agent / OpenClaw 工具设计

OpenClaw 在 MVP 中不是单纯聊天入口，而是 Agent 调度中枢。

### 10.1 建议注册的工具

#### create_dinner_task

创建多人约饭任务，返回 task_id 和 share_url。

#### submit_preference

写入某个成员的偏好。

#### extract_constraints

从发起人需求和成员偏好中抽取结构化约束。

#### detect_conflicts

识别多人之间的冲突。

#### search_restaurants

基于约束检索 mock 餐厅库。

#### score_candidates

计算每个候选方案对每个成员的满意度。

#### audit_plan

检查候选方案是否满足预算、时间、距离、忌口、氛围、排队、公平性。

#### generate_group_copy

生成群聊邀约文案。

#### save_memory

饭后根据反馈更新个人 / 小团体偏好。

### 10.2 Agent 运行流程

```text
用户发起任务
→ create_dinner_task
→ 成员提交偏好
→ extract_constraints
→ detect_conflicts
→ search_restaurants
→ score_candidates
→ audit_plan
→ 不合格则重排或降级
→ generate_group_copy
→ 输出结果
→ save_memory，可选
```

## 11. 约束抽取格式

### 11.1 硬约束

硬约束不可违反，违反则淘汰或强降级。

示例：

```json
{
  "type": "diet",
  "key": "no_spicy",
  "owner": "阿杰",
  "priority": "hard",
  "source_text": "我完全不吃辣"
}
```

常见硬约束：

- 不吃辣；
- 过敏；
- 预算上限；
- 必须几点前离开；
- 距离不能太远；
- 不能排长队；
- 营业时间必须覆盖。

### 11.2 软偏好

软偏好尽量满足，用于排序和解释。

示例：

```json
{
  "type": "taste",
  "key": "prefer_spicy",
  "owner": "小林",
  "priority": "soft",
  "source_text": "我想吃辣"
}
```

常见软偏好：

- 想吃辣；
- 有新鲜感；
- 安静；
- 适合聊天；
- 便宜一点；
- 不想火锅；
- 离学校近。

## 12. 推荐与自检逻辑

### 12.1 推荐流程

```text
1. 读取任务和成员偏好
2. 抽取约束
3. 识别冲突
4. 从餐厅库中过滤明显违规项
5. 给每个成员计算满意度
6. 给每个方案计算总分
7. 自检模块检查候选方案
8. 选择最终推荐和备选方案
9. 生成解释与群聊文案
```

### 12.2 硬约束过滤

示例规则：

```text
如果有人 no_spicy=true，则餐厅 supports_non_spicy 必须为 true。
如果预算上限为 100，则 avg_price > 100 的餐厅不作为首推。
如果有人 20:30 前要回宿舍，则 walk_minutes + eating_minutes + buffer 必须可行。
如果要求适合聊天，则 quiet_score >= 4.0 且 chat_friendly=true。
如果要求不排队，则 queue_risk 不能是 high。
```

### 12.3 满意度评分

可以先用简单公式：

```text
单人成员满意度 = 50 基础分
+ 满足软偏好加分
- 轻微违背软偏好扣分
- 风险因素扣分
```

示例：

```text
满足想吃辣：+15
支持不辣：+20
人均低于预算：+15
步行 15 分钟内：+10
安静适合聊天：+10
排队风险 medium：-8
排队风险 high：-20
人均超过个人预算：-20
```

### 12.4 群体公平性评分

不要只看平均满意度，还要看最低满意度。

建议公式：

```text
方案总分 = 平均满意度 * 0.6 + 最低个人满意度 * 0.3 + 可执行性分 * 0.1
```

这样可以避免“两个人很满意，一个人完全不能接受”。

### 12.5 自检项

| 自检项 | 通过标准 |
|---|---|
| 预算检查 | 不超过总体预算；首推尽量接近个人预算 |
| 忌口检查 | 不违反不吃辣、过敏等硬约束 |
| 时间检查 | 能按时结束并返回 |
| 距离检查 | 步行 / 通勤时间合理 |
| 营业时间检查 | 到店时间在营业时间内 |
| 排队检查 | 不选择高排队风险作为首推 |
| 氛围检查 | 安静度和聊天友好度满足 |
| 公平性检查 | 最低个人满意度不能过低 |

### 12.6 自检失败后的动作

| 失败类型 | 动作 |
|---|---|
| 预算超限 | 降级为备选或重新筛选低价餐厅 |
| 忌口冲突 | 直接淘汰 |
| 时间不可行 | 重新选更近 / 低排队风险的店 |
| 氛围不合适 | 降级为备选 |
| 某人满意度过低 | 重新找更公平方案 |
| 信息不足 | 追问，例如“你们大概几点出发？” |

## 19. 风险与降级方案

### 风险 1：OpenClaw 微信入口不稳定

降级：做模拟微信聊天页，仍然让 OpenClaw 作为后端 Agent 中枢。

### 风险 2：真实多人协同调试麻烦

降级：同一个页面提供 3 个角色输入框，演示多人数据汇总。

### 风险 3：LLM 抽取不稳定

降级：增加快捷字段，例如预算、是否吃辣、最晚回去时间；自然语言作为补充。

### 风险 4：推荐结果不稳定

降级：固定 demo task + 固定 mock 数据 + 固定候选结果；现场展示时仍调用部分逻辑。

### 风险 5：H5 部署不稳定

降级：本地启动 + ngrok / Cloudflare Tunnel；答辩现场准备录屏。

## 22. 一句话总结

这个 MVP 的本质不是“做一个网页推荐餐厅”，而是：

> 用 H5 解决微信群多人偏好收集，用后端保存任务状态，用 OpenClaw 调度 Agent 工具链，用自检模块保证推荐可靠，最终把一次多人约饭从“群里吵半天”推进到“可执行方案”。
