## 1. 一句话描述

我基本认同“全天候私人管家”的主方向：在微信小程序或类小程序入口中，做一个围绕年轻人本地生活的 AI 管家。它不是简单回答问题，而是在一天中几个关键时刻主动出现，结合天气、日程、位置、预算、历史偏好等信息，帮助用户完成吃饭、约局、周末规划、夜间突发等本地生活任务。

在这个基础上，我认为可以重点强化两个能力：

1. **自检评测闭环**：管家在输出方案前，先检查预算、时间、距离、口味、可执行性等约束，不合格就自动修正或追问；
2. **多人协同决策**：把“几个人怎么约成”作为一个核心场景，让管家不只服务单人，而是能协调多个人的偏好、冲突和限制。

一句话概括：

> 做一个会主动出现、能跨工具执行、能协调多人决策，并且会自我检查方案可靠性的本地生活 AI 管家。

## 2. 针对什么人群 / 场景

### 2.1 目标人群

主要面向 18-30 岁左右的新一代年轻人，包括：

- 在校大学生、研究生；
- 刚进入职场的年轻白领；
- 刚到新城市实习、工作或读书的人；
- 独居、合租、校园生活半径较固定的人；
- 经常需要约饭、约会、聚会、周末出行的人；
- 对 AI 工具有接受度，但又不想把所有生活决策都自己查一遍的人。

### 2.2 典型用户画像

**小林，22 岁，大学生 / 研究生，生活在学校周边。**

小林的生活特点：

- 平时学习、项目、实习比较忙；
- 每天都会遇到“吃什么、去哪、和谁约、怎么安排”的小决策；
- 一个人用美团 / 大众点评查店还可以，但多人约饭就会变得很麻烦；
- 朋友之间经常出现口味、预算、时间、距离冲突；
- 已经习惯使用大模型，但普通聊天机器人给出的建议不一定可靠；
- 希望有一个“懂我，也能帮我协调朋友”的本地生活管家。

### 2.3 聚焦的关键时刻

不建议一开始把所有本地生活场景都做全，而是聚焦几个高频、好展示、能体现 Agent 价值的场景：

| 时刻 / 场景 | 用户痛点 | 管家动作 |
|---|---|---|
| **午饭 / 晚饭决策** | 每天纠结吃什么，选择成本高 | 根据历史偏好、预算、天气、距离主动推荐 |
| **多人约饭 / 约局** | 多个人口味、预算、时间、地点冲突 | 收集偏好，识别冲突，生成折中方案 |
| **周末闲时规划** | 想出去但懒得做攻略 | 根据心情、天气、预算、同行人生成路线 |
| **夜间突发兜底** | 深夜胃痛、临时买药、忘带钥匙等情况慌乱 | 推荐 24h 服务、路线、风险提示和紧急联系人 |

其中，我认为 **多人约饭 / 约局** 可以作为最值得打穿的核心 Demo 场景。

## 3. 解决什么痛点

### 痛点 1：本地生活服务很多，但用户缺少一个统一的“管事入口”

现在用户要完成一次本地生活决策，往往需要来回切换多个工具：

- 美团 / 大众点评看店；
- 地图看路线；
- 微信和朋友讨论；
- 小红书查攻略；
- 天气 App 看天气；
- 日历看时间安排。

这些工具本身都很成熟，但它们更像“工具箱”，不是“管家”。用户仍然要自己做大量比较、筛选、协调和决策。

### 痛点 2：普通 AI 助手容易“说得像真的”，但不一定可靠

大模型可以很快生成餐厅推荐、路线规划、周末活动安排，但它常常存在几个问题：

- 忘记预算；
- 忘记某个人不吃辣、过敏或赶时间；
- 路线安排不现实；
- 推荐内容没有经过可执行性检查；
- 信息不足时不追问，直接硬生成；
- 输出很漂亮，但用户真正执行时会踩坑。

所以，生活管家不能只会生成答案，还要会检查答案。

### 痛点 3：多人场景是本地生活高频场景，但也是现有产品的弱点

很多本地生活消费并不是一个人完成的，而是几个人一起发生的：

- 朋友约饭；
- 情侣约会；
- 室友聚餐；
- 社团团建；
- 小组线下讨论；
- 家庭出行。

多人场景真正麻烦的地方不在于“找不到店”，而在于“每个人都有自己的限制”。例如：

- A 想吃辣，B 完全不吃辣；
- A 想省钱，B 想吃好一点；
- A 想拍照，B 不想走太远；
- C 晚上 8 点半前必须回去；
- 有人讨厌排队，有人只关心口味。

普通推荐系统大多默认服务单个用户，很难处理这种多人协商问题。

## 4. MVP（最小可行版本）长什么样

### 4.1 MVP 总体形式

做一个 Web / 小程序风格的 Demo，重点展示一个完整的“多人约饭管家”流程。

这个 MVP 不追求覆盖所有场景，而是先把一个高频场景打穿：

> 发起约饭 → 收集成员偏好 → 识别冲突 → 生成候选方案 → 自检评测 → 推荐最终方案 → 生成群聊邀约 / 预约 / 导航 → 饭后反馈与记忆更新。

### 4.2 输入

发起人输入：

> 明晚想和两个朋友在学校附近吃饭，人均 100 以内，适合聊天，别太吵。

随后不同成员补充偏好：

> 小林：我想吃辣，但不想吃火锅。  
> 阿杰：我完全不吃辣，预算最好别超过 80。  
> 小周：我 8 点半前要回宿舍，最好别排队，离学校近一点。

### 4.3 输出

系统输出的不只是“三家餐厅”，而是一组经过协调的方案：

- 抽取每个人的硬约束和软偏好；
- 标出主要冲突；
- 如果信息不足，主动追问；
- 生成 2-3 个候选方案；
- 说明每个方案满足了谁、牺牲了什么；
- 用自检评测模块检查预算、时间、距离、口味、公平性、可执行性；
- 推荐一个最稳妥的最终方案；
- 生成群聊邀约文案、预约提醒、导航入口；
- 饭后收集反馈，更新个人和小团体偏好。

### 4.4 最核心的功能

**多人偏好协调 + 方案自检修正。**

不是让 AI “直接推荐”，而是让 AI 像一个真正管家一样：

1. 先理解每个人；
2. 再判断冲突在哪里；
3. 再生成折中方案；
4. 再检查方案是否可靠；
5. 最后把事情推进到可执行动作。

## 5. 大概的技术方向

### 5.1 核心架构

```text
用户 / 多人偏好输入
        ↓
私人管家 Agent
- 理解任务
- 抽取偏好
- 调用工具
- 生成候选方案
        ↓
自检评测 Agent / 审计模块
- 预算检查
- 距离检查
- 时间检查
- 口味禁忌检查
- 多人公平性检查
- 可执行性检查
        ↓
方案修正 / 追问
- 信息不足则追问
- 方案不合格则重排
        ↓
最终推荐方案
        ↓
模拟执行
- 群聊邀约
- 预约 / 排队提醒
- 导航
        ↓
用户反馈
        ↓
记忆更新
```

### 5.2 涉及技术

- **OpenClaw / Agent 工具调用**：作为跨工具执行中枢；
- **大模型对话与理解**：用于解析用户自然语言需求；
- **结构化信息抽取**：把每个人的偏好抽成约束；
- **Mock POI 数据库**：模拟餐厅、活动、药店等本地生活资源；
- **规则过滤**：先排除违反硬约束的方案；
- **评分函数**：计算每个方案对不同成员的满意度；
- **LLM-as-a-Judge / 自检评测**：检查方案是否可靠；
- **记忆模块**：记录个人偏好与小团体偏好；
- **前端展示**：任务卡、冲突卡、方案卡、评测面板、记忆卡。

### 5.3 MVP 阶段的数据策略

第一版不强依赖真实美团接口，可以先使用 mock 数据。  
餐厅数据可以设计成结构化字段，例如：

```text
名称
类型
人均价格
距离
步行时间
营业时间
口味标签
是否可选辣度
安静程度
适合人数
排队风险
评分
是否适合聊天
```

这样就能支持预算、距离、时间、口味、氛围等约束判断。

### 5.4 简化实现思路

MVP 可以先做得足够清晰，而不是一开始追求完全自动化：

1. 准备 30-50 条模拟餐厅 / 活动数据；
2. 使用大模型抽取每个人的偏好；
3. 用规则过滤硬约束；
4. 用简单评分函数计算满意度；
5. 用评测模块检查结果；
6. 前端清晰展示“为什么推荐这个方案”。

## 6. 我最想做这个的原因

我认同“全天候私人管家”这个大方向，因为它很贴近本地生活的未来形态：用户不想再自己打开一堆 App 慢慢查，而是希望有一个 AI 帮他理解需求、调用工具、推进执行。

但我也觉得 01 赛道很容易同质化。很多队伍可能都会做成“美团版 AI 助手”：

> 用户问一句，AI 推荐几个餐厅 / 路线 / 活动。

所以我们需要在原有“主动管家 + 跨工具执行”的基础上，找到更有辨识度的切入点。

我认为 **多人协同** 和 **自检评测闭环** 是两个比较适合的增强方向：

- 多人协同让方案从“单人推荐”升级成“群体决策”；
- 自检评测让方案从“生成建议”升级成“可靠执行”；
- 两者都能帮助我们避免普通聊天机器人式的同质化；
- 这两个方向也比较适合我们队伍：系统工程能力可以搭框架，管理/审计背景可以参与评测和规则设计，我可以参与需求拆解、产品逻辑和 Demo 叙事。

## 7. 不确定 / 想问的问题

### 技术类

- OpenClaw 具体能否顺滑接入我们设计的工具链？
- 多人输入第一版是否需要真实多人在线，还是用模拟角色即可？
- 自检评测模块以规则为主，还是以 LLM-as-a-Judge 为主？
- 记忆模块第一版用 JSON / SQLite 是否足够？
- 小程序、网页、还是类小程序 Demo，哪种开发成本最低？

### 数据类

- 是否能获得真实美团 / 大众点评数据？
- 如果不能，mock 数据做到什么规模才有真实感？
- 餐厅字段如何设计，才能支撑预算、距离、口味、环境、排队、营业时间等判断？

### 产品类

- “全天候私人管家”是否要一开始覆盖多个场景，还是先把“多人约饭”打穿？
- 夜间突发兜底是否作为主线功能，还是作为“全天候”概念的补充演示？
- 主动推送是否要真实实现，还是用时间轴模拟即可？

### 评审类

- 官方更看重 OpenClaw 使用深度，还是更看重本地生活业务落地？
- 如果我们重点做“多人协同”，会不会被认为偏离“私人管家”的原题？
- 是否可以把多人约饭解释为全天候私人管家的第一个高频落地入口？

## 8. 已经想到的参考

- 美团 / 大众点评：餐饮、到店、评价、团购、预约；
- 微信群投票 / 群接龙：可以收集意见，但不会智能协调；

- 日程助手 / 个人助理类产品：有提醒能力，但缺少交易和本地服务场景；
- LLM-as-a-Judge / Agent Evaluation：可用于方案质量检查；
- 多目标推荐 / 群体推荐系统：可用于多人偏好平衡；
- 审计思维：把 AI 输出视为一个方案，对其进行约束检查、风险识别和修正。

## 9. 为什么我认为 01 赛道最适合我们队伍

在几个命题赛道里，我认为 01“全天候私人管家”最适合我们队伍当前的能力结构。这个判断不是因为它最简单，而是因为它最能发挥我们现有优势，同时也能避开一些明显不适配的技术坑。

### 9.1 01 赛道最吃“系统工程 + 产品叙事 + AI 工具调用”，这和我们队伍比较匹配

01 赛道的本质不是单点算法竞赛，而是一个完整的 AI Agent 产品原型：

```text
用户需求
→ Agent 理解
→ 工具调用
→ 方案生成
→ 可视化展示
→ 反馈与记忆
```

这类项目很看重系统搭建能力、工程整合能力、产品场景设计和答辩叙事。  
我们队伍里研究生学长是比较强的系统工程师，有嵌入式开发、芯片测试和复杂系统实现经验，这类能力更适合搭建 Agent 工具链和整体 Demo，而不是单纯做某个孤立算法。

我这边可以承担需求拆解、产品逻辑、文档组织、Demo 剧本和答辩表达。  
管理学院同学虽然学的是审计，不一定直接对应旅游规划，但审计背景天然关注规则、风险、流程、证据和评价标准，这反而很适合参与“自检评测模块”的指标设计，比如预算是否超限、硬约束是否满足、方案是否存在风险等。

所以 01 赛道可以让我们每个人都有比较自然的发挥空间。

### 9.2 相比 03 和 04，01 的技术风险更可控

命题 03“美甲 AI 试戴与智能运营”很依赖计算机视觉、图像分割、AR 贴图和视觉效果。  
如果 Demo 做得好，会很吸睛；但如果贴图不准、边缘粗糙、视觉效果不稳定，问题也会非常明显。我们队伍目前没有特别明确的 CV / 图像处理 / 设计强项，所以这个方向不太稳。

命题 04“配送分配 AutoSolver”非常贴近美团核心业务，上限很高，但也很吃运筹优化、组合优化、调度仿真、baseline 和指标评估。  
如果没有真正的优化建模和仿真系统，很容易变成“让大模型生成配送建议”，说服力会不足。我们队伍目前没有明确的运筹优化强者，因此主攻 04 风险偏高。

相比之下，01 的核心难度更多是系统整合和产品闭环，而不是某个特别硬的数学或视觉算法。它的技术挑战仍然存在，但更适合通过 OpenClaw、LLM、规则系统、mock 数据和前端 Demo 组合完成。

### 9.3 相比 05 / 06，01 的上限更高，也更容易形成完整产品故事

命题 05“AI 本地路线智能规划”和命题 06“周末闲时活动规划”都比较容易做出 Demo，但也更容易同质化。  
很多队伍可能都会做成：

```text
输入时间 + 预算 + 地点 + 偏好
→ AI 生成路线 / 周末计划
```

这类方案直观、好展示，但如果没有明显创新，很容易变成普通“AI 攻略生成器”。

01 赛道可以把 05 / 06 的路线规划、活动规划吸收为“私人管家”的子场景。  
也就是说，我们不一定要单独做路线规划，而是可以把它放在“管家主动规划周末”或“多人约局后安排路线”的流程里。这样既保留 05 / 06 的直观 Demo，又能放进更大的 Agent 故事线中。

### 9.4 02 赛道可以作为 01 的增强能力，而不是单独竞争主线

命题 02“复杂指令下的多轮对话评测系统”本身很有技术深度，也不容易和普通 AI 助手撞车。  
但如果单独做 02，可能会比较偏工具化、评测平台化，答辩时不如 01 的“本地生活管家”直观。

更好的方式是把 02 的思想嵌入 01：

```text
管家生成方案
→ 自检评测模块检查约束
→ 不合格则追问或修正
→ 用户反馈写入记忆
```

这样 02 不再是一个单独赛道，而是 01 的可靠性机制。  
这也正好和管理学院审计同学的背景形成联系：把 AI 输出当作一个“方案”，对它进行规则检查、风险识别和可执行性评估。

### 9.5 01 赛道虽然同质化严重，但我们可以用“多人协同 + 自检闭环”拉开差异

01 最大的问题是很多队伍都会做“本地生活 AI 助手”。  
如果我们只是做一个聊天框，让用户问“今天吃什么”，AI 推荐三家餐厅，那一定不够。

但我们可以把重点放在两个更有辨识度的方向：

```text
1. 多人协同：解决几个人约饭、约会、聚会时的口味、预算、时间、距离冲突；
2. 自检评测：让 AI 方案在输出前经过预算、忌口、距离、时间、公平性和可执行性检查。
```

这两个点可以把作品从“AI 推荐助手”升级为“会协调、会审计、会修正、会执行的生活管家”。

### 9.6 对各赛道的简要判断

| 赛道 | 优势 | 风险 | 对我们队伍的适配度 |
|---|---|---|---|
| **01 全天候私人管家** | 最贴合本地生活 Agent，产品故事完整，可发挥系统工程能力 | 同质化严重，需要做出差异化 | **最高，建议主推** |
| **02 多轮对话评测系统** | 技术深度强，可做指标和评测 | 单独做不够直观，业务故事偏弱 | **适合作为 01 的增强模块** |
| **03 美甲 AI 试戴** | 视觉效果好则很吸睛 | 吃 CV / AR / 设计能力，失败很明显 | **偏低** |
| **04 配送分配 AutoSolver** | 贴近美团核心业务，上限高 | 运筹优化和仿真难度高 | **偏低，除非有强算法支撑** |
| **05 本地路线规划** | 直观、好做 Demo | 容易变成普通路线生成器 | **可作为 01 子场景** |
| **06 周末活动规划** | 容易落地，产品感强 | 同质化严重，上限有限 | **可作为 01 子场景** |
| **开放赛道** | 自由度高，不容易撞题 | 需要自己证明题目价值，容易散 | **可作为备选，不如 01 稳** |

### 9.7 小结

因此，我倾向于把 01 作为主赛道，但不要做成泛泛的“万能生活助手”。  
更合适的路线是：

```text
主线：基于 OpenClaw 的全天候私人管家
切口：多人约饭 / 多人活动协同
增强：自检评测闭环
扩展：午饭推荐、周末规划、夜间突发等更多本地生活场景
```

这样既延续了 01 赛道的官方主题，又吸收了 02 的技术深度，同时避开 03 / 04 的高不确定性和 05 / 06 的强同质化。

# 10. 对现有 01 方案的两个增强建议

我认为现有“全天候私人管家”的主线已经很清晰，尤其是“主动出现”和“跨工具执行”这两个点很重要。  
在这个基础上，我建议重点补充两个增强方向：

1. **自检评测闭环**：让管家不只是生成方案，而是在输出前检查方案是否可靠；
2. **多人协同决策**：让管家不只服务单人，而是解决多人本地生活决策中最麻烦的协调问题。

这两个增强点的目标不是另起一个新方案，而是让 01 方案更有辨识度、更不容易同质化，也更像一个可落地的真实 Agent 产品。

---

## 11. 创新点一：自检评测闭环

### 10.1 为什么这个点重要

如果我们只做一个“AI 本地生活助手”，很容易出现一个问题：  
AI 的回答看起来很顺，但不一定真的能执行。

例如用户说：

> 明晚三个人约饭，人均 100 以内，一个人不吃辣，一个人 8 点半前要回宿舍。

普通 AI 可能会直接推荐几家店，但它未必真的检查：

- 是否超预算；
- 是否有人不能吃辣；
- 是否能按时回去；
- 路线是否过远；
- 是否适合聊天；
- 是否所有人都被照顾到。

所以，我建议在管家 Agent 之后加入一个“自检评测模块”，让它像一个审计员一样检查方案。

### 10.2 它和命题 02 的关系

命题 02 是“复杂指令下的多轮对话评测系统”。  
如果我们单独做 02，可能会比较偏工具化、偏评测平台，不如 01 的产品故事直观。

但如果把 02 的思想嵌入 01，就可以形成更紧密的融合：

```text
不是“做完管家后顺便评测一下”，
而是“管家每次输出前都要经过评测模块检查”。
```

这样 02 就不是外挂，而是 01 的核心可靠性机制。

### 10.3 运行流程

普通 AI 助手流程：

```text
用户输入 → AI 生成方案 → 直接输出
```

我们的流程：

```text
用户输入
→ 管家 Agent 生成候选方案
→ 自检评测模块检查预算 / 时间 / 距离 / 口味 / 公平性 / 可执行性
→ 如果不合格，自动修正或追问
→ 输出最终方案
→ 用户反馈
→ 更新个人与小团体记忆
```

### 10.4 自检模块检查什么

可以先设计几个明确指标：

| 检查项 | 说明 |
|---|---|
| **预算检查** | 是否超过用户预算或成员预算上限 |
| **时间检查** | 是否满足结束时间、营业时间、路程时间 |
| **距离检查** | 是否过远，是否绕路 |
| **口味 / 禁忌检查** | 是否违反不吃辣、过敏、忌口等硬约束 |
| **氛围检查** | 是否适合聊天、约会、团建等场景 |
| **公平性检查** | 是否明显牺牲某一个成员 |
| **可执行性检查** | 是否有排队风险、关门风险、路线不合理等问题 |

### 10.5 自检如何反过来帮助管家运行

这个模块不是只负责“打分”，而是直接影响管家的下一步动作：

| 自检发现的问题 | 管家动作 |
|---|---|
| 信息不足 | 主动追问最关键问题 |
| 预算超限 | 重新筛选低价方案 |
| 违反忌口 | 直接淘汰该候选 |
| 距离过远 | 换更近的店或重排路线 |
| 某个成员满意度过低 | 重新生成更公平的折中方案 |
| 方案可执行性低 | 输出风险提示或备选方案 |
| 用户反馈不满意 | 写入记忆，下次避开类似推荐 |

这样，自检评测模块会形成一个闭环：

```text
计划前：判断信息是否足够
计划中：检查方案是否满足约束
计划后：根据反馈更新记忆
下一次：基于记忆生成更好的方案
```

### 10.6 这个创新点的亮点

- 能把 01 和 02 融合得更紧，不是简单拼接；
- 让作品看起来更像真实工程系统，而不是普通聊天框；
- 适合展示“普通 Prompt vs 加入自检模块”的对比；
- 可以用指标证明方案质量，而不是只靠主观讲故事；
- 管理 / 审计背景的队友可以参与规则设计和风险识别。

### 10.7 可能难点

- 自检规则不能太空泛，需要明确字段和判断标准；
- LLM-as-a-Judge 可能不稳定，最好结合规则检查；
- 如果 mock 数据太少，自检结果会显得假；
- 如果指标太多，MVP 会变复杂，第一版要控制范围。

## 12. 创新点二：多人协同决策

### 11.1 为什么这个点重要

本地生活里，很多消费不是一个人发生的，而是多人发生的。  
但多人场景最麻烦的不是“找不到店”，而是“大家很难达成一致”。

例如：

```text
A：想吃辣，但不想吃火锅
B：完全不吃辣，预算最好低一点
C：8 点半前要回宿舍，不想排队
```

普通推荐系统通常默认服务发起人。  
但一个真正的生活管家应该能服务整个小团体，帮大家找到都能接受的方案。

### 11.2 多人协同的核心逻辑

我建议把多人协同做成六步：

```text
1. 发起人创建本地生活任务
2. 成员用自然语言补充偏好
3. 系统抽取硬约束和软偏好
4. 系统识别冲突并决定是否追问
5. 系统生成多个折中方案
6. 系统用公平性指标选择最终推荐
```

这里最重要的是区分：

- **硬约束**：不能违反，例如过敏、不吃辣、预算上限、必须几点前离开；
- **软偏好**：尽量满足，例如想吃辣、想拍照、想安静、想有新鲜感。

硬约束优先级最高，软偏好用于排序和解释。

### 11.3 冲突识别

系统要能明确告诉用户冲突在哪里。  
例如：

```text
我发现你们主要有三个冲突：

1. 口味冲突：小林想吃辣，但阿杰完全不吃辣；
2. 时间冲突：小周 8 点半前要回宿舍，所以不能选太远或排队久的店；
3. 预算冲突：总体预算人均 100，但阿杰更希望不超过 80。
```

这个“识别冲突”的过程很重要。  
它会让用户感觉 AI 不是在随机推荐，而是真的理解了多人需求。

### 11.4 方案生成方式

不要只输出一个“最佳答案”，而是输出几个策略不同的方案：

```text
方案 A：最公平折中
方案 B：最省时间稳妥
方案 C：最有新鲜感
```

每个方案都说明：

- 满足了哪些硬约束；
- 照顾了哪些人的偏好；
- 牺牲了什么；
- 有什么风险；
- 为什么推荐或不推荐。

### 11.5 公平性指标

多人决策不能只看平均满意度。  
因为可能出现一种情况：两个人很满意，一个人完全不能接受。平均分看起来不错，但实际无法成行。

所以可以加入一个简单原则：

> 不只看平均满意度，也要看最低个人满意度。

例如：

```text
方案总分 = 平均满意度 × 0.7 + 最低个人满意度 × 0.3
```

同时设置硬约束淘汰规则：

```text
只要违反任何成员的硬约束，该方案直接降级或淘汰。
```

这样可以避免某个人被明显牺牲。

### 11.6 多人协同的亮点

- 比单人推荐更有复杂度，更能体现 Agent 价值；
- 非常贴合美团餐饮、到店、活动、团购等业务；
- 容易做出清晰 Demo，评委能快速理解；
- 可以和微信群、群聊邀约、投票确认等真实场景结合；
- 能和自检评测模块自然融合，形成“生成—检查—协商—执行”的链路。

### 11.7 可能难点

- 第一版如果做真实多人在线，开发成本可能偏高；
- 成员偏好抽取要尽量稳定，否则后续推荐会乱；
- 公平性指标不能太复杂，否则难以解释；
- 需要足够丰富的 mock 数据字段，才能支持多人约束判断。

### 11.8 可行的降级方案

第一版不用做真实多人在线，可以用三个模拟角色完成演示：

```text
发起人：小林
成员 1：阿杰
成员 2：小周
```

前端展示三个人的输入框即可。  
等核心流程跑通后，再考虑真实邀请、群聊分享或多人投票。

## 13. Demo 剧本：三人周五约饭

### 12.1 发起任务

用户输入：

> 明晚想和两个朋友在学校附近吃饭，人均 100 以内，适合聊天，别太吵。

系统生成任务卡：

```text
任务：周六晚三人约饭
人数：3
预算：≤100 元/人
地点：学校附近 3km
氛围：安静、适合聊天
状态：等待成员补充偏好
```

### 12.2 成员补充偏好

```text
小林：我想吃辣，但不想吃火锅。
阿杰：我完全不吃辣，预算最好别超过 80。
小周：我 8 点半前要回宿舍，最好别排队，离学校近一点。
```

### 12.3 系统识别冲突

```text
我发现你们主要有 3 个冲突：

1. 口味冲突：小林想吃辣，但阿杰完全不吃辣；
2. 时间冲突：小周 8 点半前要回宿舍，因此不能选择太远或排队久的店；
3. 预算冲突：总体预算是人均 100，但阿杰更希望不超过 80。

我会优先保证“不吃辣、时间限制、预算上限”等硬约束，再尽量满足小林想吃辣和大家想安静聊天的软偏好。
```

### 12.4 系统生成候选方案

```text
方案 A：学校东门融合菜
- 人均：82 元
- 距离：步行 12 分钟
- 等位风险：低
- 氛围：安静，适合聊天
- 适配理由：有不辣菜，也有可选辣菜，不是火锅
- 满意度：小林 82 / 阿杰 94 / 小周 90
- 自检结果：通过

方案 B：烤肉店
- 人均：108 元
- 距离：打车 10 分钟
- 氛围：偏热闹
- 风险：略超预算，聊天环境一般
- 满意度：小林 88 / 阿杰 76 / 小周 70
- 自检结果：预算和安静度不足，不作为首推

方案 C：轻食西餐
- 人均：78 元
- 距离：步行 8 分钟
- 氛围：安静
- 风险：小林“想吃辣”的偏好满足较弱
- 满意度：小林 65 / 阿杰 92 / 小周 95
- 自检结果：可作为保守备选
```

### 12.5 最终推荐

```text
综合来看，我推荐方案 A。

原因：
- 没有违反任何人的硬约束；
- 人均 82 元，符合总体预算，也接近阿杰的预算偏好；
- 步行 12 分钟，能保证小周 8 点半前回宿舍；
- 有不辣菜，也有可选辣菜，能兼顾小林和阿杰；
- 环境相对安静，适合聊天；
- 三个人的最低满意度最高，没有明显牺牲某一个人。
```

### 12.6 一键后续动作

```text
可执行动作：
1. 生成群聊邀约文案；
2. 模拟预约 / 排队提醒；
3. 生成导航路线；
4. 饭后询问反馈；
5. 更新三人小团体偏好。
```

## 14. 为什么这两个创新点能增强原方案

### 13.1 对抗同质化

01 赛道很容易变成“AI 生活助手”大混战。  
如果我们只做推荐，很容易和其他队撞车。

但如果我们强调：

```text
主动式管家
+ 跨工具执行
+ 多人协同
+ 自检评测闭环
```

就会比普通聊天机器人更有辨识度。

### 13.2 更贴近真实生活

真实生活里，很多问题不是“我想去哪”，而是：

```text
我们几个人怎么约？
谁的限制不能违反？
哪个方案大家都能接受？
这个方案真的来得及吗？
预算会不会超？
```

多人协同和自检评测正好对应这些真实问题。

### 13.3 更容易展示技术深度

普通推荐 Demo 可能看起来只是 Prompt 工程。  
但加入自检和多人协同之后，可以展示：

- 信息抽取；
- 约束建模；
- 冲突检测；
- 规则过滤；
- 多目标评分；
- LLM 解释生成；
- 评测指标；
- 记忆更新。

这样更像一个系统工程项目。

### 13.4 更适合团队分工

- 系统工程强的同学可以搭 Agent 和工具调用；
- 管理 / 审计背景同学可以参与用户场景、规则、风险和评测指标；
- 我可以参与需求拆解、产品逻辑、Demo 剧本和答辩表达；
- 如果需要外部顾问，也可以帮助检查评分逻辑和可行性。

## 15. 可能遇到的难题与 Plan B

### 难题 1：功能范围过大

如果同时做午饭、约饭、周末、夜间突发，可能每个场景都不够深。

**Plan B**：优先收窄成“多人约饭管家”，把一个场景打穿。

### 难题 2：真实数据难拿

没有真实美团接口时，推荐和执行可能显得假。

**Plan B**：使用高质量 mock 数据，字段做细，让逻辑真实。重点展示系统流程，而不是宣称已经接入真实交易。

### 难题 3：自检评测容易变成概念

如果只是让大模型说“这个方案不错”，说服力不够。

**Plan B**：规则检查 + LLM 解释结合。预算、时间、距离、忌口等硬指标用规则，方案解释和软偏好用 LLM。

### 难题 4：多人协同开发成本高

真实多人在线、群聊同步、投票系统可能开发量大。

**Plan B**：第一版用模拟三角色 + 单页面流程，先把核心逻辑讲清楚。

### 难题 5：偏离“全天候私人管家”主线

如果过度强调多人约饭，可能被认为太窄。

**Plan B**：把多人约饭定义成“全天候私人管家”的第一个高频落地场景。后续可扩展到周末活动、夜间突发、旅行规划等更多场景。

## 16. 总结

我认为当前 01 方向的基础主线可以保持不变：  
**做一个基于 OpenClaw 的本地生活全天候私人管家。**

我的补充建议是，不要把它做成普通“AI 推荐助手”，而是在原方案基础上突出两个增强点：

1. **自检评测闭环**：让管家生成方案后先检查、再修正、再输出，并根据反馈持续学习；
2. **多人协同决策**：把约饭、约会、聚会等多人本地生活场景作为核心切入点，解决真实生活里“几个人怎么约成”的问题。

如果这两个点能做出来，这个方案会从“一个会聊天的本地生活助手”升级成：

> 一个会主动出现、理解多人、识别冲突、审计约束、修正方案、推进执行、持续学习的本地生活 Agent。

这可能是我们在 01 赛道里避免同质化、做出辨识度的一条可行路线。
